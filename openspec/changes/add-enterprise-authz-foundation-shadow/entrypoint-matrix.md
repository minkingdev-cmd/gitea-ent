## 跨入口去重与阶段：基于现有调用链

1. **文件修改不是纯 router 操作。** Web/API 的单文件、批量、上传走 `ChangeRepoFiles`，patch/cherry-pick 另走 `gitPatchCommitPush`；这些最终调用 `TemporaryUploadRepository.Push`，后者设置 `modules/repository/env.go:PushingEnvironment`。同一次改文件可能在 router、shared files service、Git hook 三层出现。应由最早安全入口生成受信 operation ID，service 接受原生 actor/permission/credential/source，按 repo/action/目标 ref 生成子 observation ID；同一个逻辑 action 完成一次，CODEOWNERS 等额外 action 则另一个子 ID。路径应包含 rename 的前后路径；递归删除/patch 若入口没有完整集合不能把单一路径当完整集。
2. **普通 push 要按 ref，而不是按 HTTP/SSH 请求。** `HookPreReceive` 循环 OldCommitIDs/NewCommitIDs/RefFullNames，并按 branch/tag/refs-for 分派；`HookPostReceive` 收集 updates。一个 receive-pack 可以包含创建、更新、删除多个 ref，不能只产生一个 branch decision；tag/wiki 不能凑数为 branch/code action。既有 GitPush 测试确有多分支同时 push 和 delete 场景。分支删除属于目标 ref 变更的现有行为，记录时须标明操作类型，不臆造新的 catalog key。
3. **Web/API/auto/force merge 有共享 service，也有 service 前拒绝。** 三者实际汇合 `pull.Merge`，但 `CheckPullMergeable` 在 router/auto 先行执行；只 hook Merge 会漏掉这些 native deny。`Merge` 新建 HammerContext，不自动继承请求上下文，且设置 `FullPushingEnvironment(..., prID, prIndex)` 后触发 receive hooks。必须设计受信观察上下文跨 HammerContext/env/internal request 传播，不能靠客户端 operation ID，也不能靠裸 doer 回读扩权。force/manual/auto 各保留实际分支；只成功排队或 skip 不是成功合并。
4. **pre-receive 与 post-receive 不是一对必达回调。** 拒绝在 pre-receive 就结束；Git 进程中止或客户端断开也可能没有完整终态。pre-receive 的“ok”表示 guard 通过，post-receive 的 DB sync 又可能失败，即使 ref 已写入。按可确认阶段填写 native_stage，无法确认全操作则 unknown；不得根据 candidate allow 推断原生成功。`cmd/hook.go` 对 `EnvIsInternal=true` 有既有 early return，因此依赖 receive hook 不能覆盖所有内部写入；不能为了观察取消这条原生短路。
5. **危险操作观察不得拿变更后对象反推。** transfer 接收会换 owner，delete 会删除对象；archive 会修改传入 repo 的 IsArchived。capture 必须在原生 Tx/资源 mutation 前且经过原生可见性，finish 必须在 Tx/业务锁结束后。`StartRepositoryTransfer` 与 `AcceptTransferOwnership` 既有全局锁、嵌套事务；共享下层 helper 适合携带一次 observation handle，但不能在锁内再开证据写 Tx。旧 owner 策略不迁移为新owner授权。
6. **共享管理 helpers 必须明确 repo scope。** webhook/secrets helpers 同时处理 user/org/system 与 repo，直接在 helper 无条件观察会把非repo操作伪造为 repo action。CI configuration 与 required checks 可共用 rule/unit更新，但 workflow dispatch/rerun/job 执行、secret读取、webhook实际投递不归 manage_ci 或管理修改成功。
7. **迁移的 Web/task 与 API 同步路径不同。** Web CreateMigrateTask 有本地 repoID 后，runMigrateTask 才负责完整迁移；task成功和 uploader Finish 有明确原生状态变化。API Migrate 先创建 target，再用 HammerContext 调用 MigrateRepository，因此也要显式保留请求的观察上下文，不能错误假设 API 已转入同一个 task。保留原 owner创建审批与URL政策；目标 repo尚不存在的错误不新查/构造资源。retry 是新操作，持久 operation/request reference 只能由服务端产生，不泄露迁移 URL、密码/token 或 provider payload。

8. **迁移前置失败审计已按用户批准补齐。** 原先 `auditNotifier` 继承 `NullNotifier.MigrateRepository`，task 状态/log/CreateRepositoryNotice 不能证明结构化审计。2026-10-01 新增 `services/enterpriseauthz/migration.go`，API/Web/task 在安全拒绝/失败边界记录 `enterprise:authz:migration:failure`，用户/明确系统作用域、ID-only、固定原因/阶段、去重、独立事务及 200ms 预算；disabled 不新增记录。`services/repository/create.go` 在受信 migration context 上注册最外层 DB after-commit 标记，避免 DB 已创建但 Git 初始化/清理失败时误记前置失败。真实 HTTP 响应对比、task 故障、残留目标、脱敏/留存/审计故障和 PG 预算测试已通过。已有目标后的 `repo.migrate` 决策、异步传播及 retry 仍属任务 8.8，不把此次非 repo 审计或成功 notify 当其完成。

## 2026-10-01 PR Web/API 切片边界

- 创建作用域为 base/target repo；head/fork 与原生 Git actor 不替换当前执行人。candidate 仅观察，不进入原生 NewPullRequest/review guard、事务或返回分支。条件只传固定 web/api source，未可信解析 branch/path 时保持 unresolved。

- handler operation 结果覆盖最终响应：Web self-review 的 HTTP 200 redirect 明确 denied；API 422 self-review/closed PR 亦为 denied。验证、存储、转换/渲染失败为 failed；failed 不表示原生已经发生的部分写入回滚。多评论/服务内部 SubmitReview 不另重复记录。
